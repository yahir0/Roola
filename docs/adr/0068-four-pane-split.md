# ADR-0068: ワークスペースを 4 分割（2×2）まで広げる

- **Status**: Accepted
- **Date**: 2026-08-06

> 実装計画は OpenSpec change `add-four-pane-split` を参照。
> ADR-0026 の「代替案 3: ペイン数・配置を任意グリッドで可変にする」の判断を一部変更する
> （Supersede ではなく、固定スロットを 3 → 4 に広げる範囲での変更）。

## Context

ワークスペースは ADR-0026 以来 `topLeft` / `topRight` / `bottom` の 3 スロット固定で、
下段は常に横いっぱいだった。ADR-0026 は代替案 3 で任意グリッドの自由分割を
「スプリッタ・ドロップ判定・永続化スキーマが大幅に複雑化する。**上 2 + 下 1 が要求の
実体であり、固定 3 スロットで十分**」として却下している。

ADR-0067 の git worktree 統合以降、「worktree 1 つにつき Claude セッション 1 つ」を
並列に走らせる使い方が中心になった。下段のターミナルが 1 面しかないと、複数の
エージェントはタブで切り替えるしかなく、進行状況を**同時に目視できない**。これは
上段でエクスプローラを 2 面並べる理由（ADR-0026 の「複数並行参照が本質的要求」）と
同じ構造の要求であり、要求の実体そのものが「上 2 + 下 1」から動いた。

## Decision

**固定スロットを 4（2×2）へ広げる。任意グリッドには踏み込まない。**

1. `PaneSlotId` を `topLeft` / `topRight` / `bottomLeft` / `bottomRight` の 4 値にする
   （`bottom` → `bottomLeft` にリネーム）。下段は上段と同じく左右 2 分割になり、
   上段とは独立したスプリッタ比率 `bottomLeftRatio` を持つ。
2. **既定は 3 分割のまま**とする。seed は `bottomRight` を空にし、空スロットは描画
   されない（既存の崩し再フロー）ため、起動直後の見た目・操作感は現行と完全に同一。
3. **4 分割への到達はユーザーの明示操作のみ**とする。タブ右クリックメニューの
   「タブを右下ペインへ移動」（新規コマンド `moveTabBottomRight` / ⌘⌃4）と、
   右下ペインが実体化した後の DnD。専用の「分割」コマンドは作らない。
4. 崩し再フローを **「上段 row × 下段 row」モデル**に一般化する。
   `WorkspaceLayoutMode` enum を廃し、`resolveWorkspaceLayout()` は各 row の非空
   スロット列 `{ topSlots, bottomSlots }` を返す。
5. **自動でタブを開く先は左下（`bottomLeft`）固定**とする。タイル右クリックの
   ターミナル / Claude / スキル、worktree 作成後の起動、Git ビューの「ターミナルを開く」、
   ノートパッドボタン、サイドバーからの起動は、下段にフォーカスがあっても `bottomLeft`
   へ開く。

## Why

- **要求の実体が変わった**: ADR-0026 の却下理由は「上 2 + 下 1 で十分」という要求認識に
  依存していた。並列エージェントの同時可視化という新しい実体に対しては、その前提が
  成り立たない。一方で「スプリッタ・ドロップ判定・永続化が複雑化する」という懸念は
  任意グリッドに固有のもので、**固定 4 スロットなら当てはまらない**
  （スロットが 1 つ増え、比率が 1 本増えるだけ）。判断の全否定ではなく射程の調整。

- **既定を変えないことで「4 分割の負担」を負わない**: ADR-0026 は「3 分割時の各ペインが
  狭い」を trade-off に挙げていた。4 分割はさらに狭くなるが、**ユーザーが明示的に選んだ
  ときだけ**その状態になる。既定 3 分割 → 明示操作で 4 分割 → タブを空にすれば 3 分割へ
  戻る、という往復が既存の崩し再フローだけで成立する。

- **row モデルで組み合わせ爆発を避けた**: 4 スロットで enum 分岐を続けると非空スロットの
  組み合わせは 15 通り、モードは最低 6 値必要になり、しかも「上 2 下 1」と「上 1 下 2」で
  `visibleSlots` の順序解釈が呼び出し側依存になる。row 単位で独立に解決すれば、
  single 〜 four がすべて 1 つの規則の帰結として出て、順序の解釈が構造に埋まる。
  3 分割は「下段が 1 つだけ → 下段が全幅」という自然な帰結で、現行と同一の描画になる。

- **新スロットの振る舞いは自動的に既存と揃う**: per-tab 状態（ADR-0027）の family キーは
  `tabId` でスロットと無関係、フォーカス追跡も `tabId` ベース、`PaneWidget` /
  `PaneTabStrip` は `slotId` を引数に取る作り、そして状態を走査する箇所はすべて
  `PaneSlotId.values` を回している。列挙値を 1 つ足すだけで、タブ操作・状態保持・
  タブ切替・通知クリックでの復帰までが同じ振る舞いになる。

- **自動起動先を左下固定にした**: 右下を「ユーザーが明示的に置いたものだけが入るペイン」
  にすることで、自動で開いたタブに作業中のセッションが押し流されない。挙動が現行から
  一切変わらないという利点もある。「フォーカス中が下段ならそのペイン」への変更は
  `_focusedSlot()` と同じ要領で後から小さく入れられるため、まず挙動不変で出して使って
  から判断する。

### 代替案 1: `WorkspaceLayoutMode` enum を 6 値へ拡張する

現行の分岐構造を保ったまま `four` と「上 1 下 2」のモードを足す案。

- 変更量は小さいが、`three` 相当が 2 種類でき、`visibleSlots` の順序をどう読むかが
  呼び出し側の暗黙知になる
- スロットを将来さらに増やすと破綻する（row モデルなら row 内の要素数が増えるだけ）
- 却下。

### 代替案 2: 上段を 3 分割にする（3 + 1）

下段は横いっぱいのまま、上段に `topCenter` を足す案。

- エクスプローラを 3 面並べる用途には合うが、要求の実体は「エージェントを 2 面並べる」
  であり、下段が 1 面のままでは解決しない
- 却下。

### 代替案 3: 任意グリッドの自由分割（再検討）

ADR-0026 代替案 3 の再検討。分割ツリー（再帰構造）でどのペインでも分割できるようにする案。

- `PaneSlotId` という固定 ID が消えるため、`PaneSlotId.values` 走査に依存している
  既存コード（provider / dispatcher / sidebar / notification）がすべて書き換えになる
- 「どのペインに開くか」を指す語彙（`bottomLeft` 等）が失われ、自動起動先の指定方法を
  再設計する必要が出る
- 要求の実体は 2×2 で満たされる。複雑度に見合わない
- 却下（ADR-0026 の判断を維持）。

## Trade-offs

- **4 分割時の各ペインが狭い**: ADR-0026 の trade-off がさらに進む。既定 3 分割 +
  明示操作でのみ 4 分割、スプリッタの比率クランプ（0.15〜0.85）と `minPaneSize` で緩和する。
- **右下ペインの生成経路が右クリックメニューのみ**: 空スロットは描画されないため、
  右下が空のうちは DnD の受け口も「+」も存在しない。最初の 1 枚は右クリックメニューで
  送る必要がある。これは既存スロットと同じ性質（`topRight` / `bottomLeft` は既定 seed で
  最初から埋まっているために表面化していなかっただけ）で、新たな例外は作らない。
- **`resolveWorkspaceLayout` の戻り値型が変わる**: `WorkspaceLayoutMode` を参照している
  テストは全面書き換えになる。実コードの参照元は `_WorkspaceArea` 1 箇所のみ。
- **`bottom` → `bottomLeft` のリネームが 15 箇所程度に及ぶ**: すべて機械的置換で挙動は
  不変。コンパイルエラーで漏れを検出できる。
